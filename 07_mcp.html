MCP server

Expose nbskill notebook operations as native MCP tools. This is the preferred integration for careful single-notebook reads and edits because multiline notebook cells travel as structured tool arguments rather than shell-quoted strings.

The server now favors verifiable context: batch edits include read-back hashes, symbol graph calls include complete structured usage data, and generated-file warnings are reserved for changes that touch exported notebook code.

The command-line functions are useful on their own, but coding agents work best when the same operations are available as structured tools. This notebook exposes the project through a FastMCP server while keeping the server layer thin and predictable.

Production contract

The MCP server exposes the production core through stable structured tools. Tool schemas exclude uncommon Python-only operations, responses include concise text plus structured content, diagnostics are scoped to touched notebooks when possible, edit tools report feedback without raw notebook JSON, and experimental tools are omitted from default production use.

The MCP server should stay boring on purpose. Each tool accepts structured arguments, captures printed output, uses notebook locks where file operations can collide, and delegates the actual work to the same functions tested elsewhere.

File-based reload imports

FastMCP 3 reload executes the selected file as an un-packaged module. nbskill.mcp therefore declares its package when needed before its relative imports run; regular package imports already have the correct package and are unchanged.

Isolated notebook operations

edit_notebook_tool and exec_nb_tool run notebook mutation and execution in importable multiprocessing workers instead of doing the work directly in MCP worker threads. This is intentional. If an MCP client times out, cancelling an asyncio.to_thread wait does not stop the underlying Python thread; the old work can keep exporting notebooks and consuming memory after the client has already given up.

A process gives the server a boundary it can terminate. The worker target is a normal module function, not a string passed to python -c, so the code is readable, importable under spawn, and covered by notebook tests. On POSIX the worker starts a process group with setsid, which lets timeout cleanup terminate nested export work too.

Each child owns the notebook locks for its actual transaction. The parent must not retain a process-scoped notebook lock while waiting for that child: the worker would block on the parent and both sides would wait until timeout. edit_notebook_tool caps tool_timeout at 110 seconds so it can return a structured timeout before clients with a 120 second transport deadline give up.

Diagnostics and log reports

The server records enough information to diagnose failures after a client disconnects. Log parsing stays separate from transport middleware so reports can be tested with small JSONL fixtures.

MCP postmortems need every tool call to leave enough evidence to answer three questions later: did it finish, how long did it take, and how much output did it produce. The middleware logs these fields at the server boundary so individual tools do not each need bespoke timing code.

The log reporter intentionally accepts older log files. Older rows do not have call ids or output lengths, so the report pairs what it can and calls out missing evidence as a problem instead of pretending the history is cleaner than it is.

Registering notebook tools

The wrapper should preserve useful structure, not flatten everything into text. context uses overview for compact versus focused detail, and project-level calls can attach the notebook knowledge graph with include_graph=True. Cell or symbol targets include symbol graph payloads so MCP clients can inspect impact without parsing prose.

Edit and execution wrappers also adapt to MCP-specific transport. update_cell accepts new_lines so exact source can be sent directly without temporary files, and unsafe exec_nb runs in an isolated process so the MCP server can terminate runaway execution without blocking worker threads.

Small MCP surface

The public MCP server exposes nine tools for the normal notebook workflow: context, edit_notebook, exec_nb, verify_change, doctor, diff_nb, create_notebook, reference, and healthcheck.

context is the only read surface: start with view="summary", then narrow by chapter, cell_type, query, include_re, exclude_re, or context_lines. Use doctor(scopes="style") for style diagnostics; there is no separate style tool.

edit_notebook supports replace_cell, insert_cells, delete_cells, move_cells, explode_cells, replace_lines, insert_lines, delete_lines, replace_text, and replace_texts. Existing cells use cell_id, cell_ids, or target="all"; whole-cell payloads use source or source_lines, structural edits use cells plus anchor_id/where, and text edits are literal. Add expected_hash when stale context must fail, and use dry_run=True to preview.

Verify explicitly affected notebooks

verify_change accepts only named notebooks. It reviews each diff, runs a safe in-memory check through the last changed code cell unless an up2id override is supplied, and scopes doctor to that notebook. The reports stay separate so one failure does not hide the results for the others.
